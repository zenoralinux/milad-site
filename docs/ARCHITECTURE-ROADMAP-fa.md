## 1. چشم‌انداز و محدوده محصول

Milad CMS یک سیستم مدیریت محتوای مستقل، قابل نصب و ماژولار است. محصول باید دو کاربرد را با یک هسته مشترک پوشش دهد:

1. **هسته عمومی CMS:** مدیریت صفحات، نوشته‌ها، رسانه، کاربران، دسترسی‌ها، قالب، تنظیمات، سئو، نسخه‌ها و API.
2. **ماژول اختصاصی پورتفولیو:** مدیریت پروژه‌ها، مهارت‌ها، دستاوردها، Timeline، وضعیت فعلی و همگام‌سازی اختیاری GitHub.

نسخه نخست برای یک وب‌سایت و یک فضای مدیریتی طراحی می‌شود؛ معماری باید امکان افزودن ماژول‌های دیگر و استفاده از CMS برای سایت‌های دیگر را فراهم کند، اما چندمستاجری (multi-tenant)، بازارچه افزونه و صفحه‌ساز آزاد با کدنویسی دلخواه جزو محدوده نسخه اول نیستند.

### تصمیم‌های قطعی

| موضوع | تصمیم |
|---|---|
| محصول | Hybrid CMS: هسته عمومی + ماژول Portfolio |
| بک‌اند | PHP اختصاصی، بدون وابستگی اجباری به Laravel |
| سبک معماری | Modular MVC و Service Layer |
| پایگاه داده | MySQL / MariaDB از طریق PDO |
| رندر سایت عمومی | Server-Side Rendering |
| ارتباطات | REST API نسخه‌بندی‌شده در مسیر `/api/v1` |
| ویرایش محتوا | Rich Block Editor + Visual Page Builder |
| رابط | فارسی و RTL در اولویت، واکنش‌گرا و قابل توسعه برای زبان‌های دیگر |
| نصب | Web Installer مرحله‌ای با قفل نصب |
| توسعه | فقط روی شاخه توسعه؛ عدم تغییر مستقیم `main` |

استفاده از Composer برای autoload و وابستگی‌های محدود مجاز است؛ اجرای سایت نباید به Node.js یا فرایند build روی هاست نهایی وابسته باشد. فایل‌های تولیدشده و کتابخانه‌های سمت مرورگر باید به‌صورت محلی ارائه شوند و به CDN خارجی وابسته نباشند.

## 2. اصول معماری

- جداسازی Core از ماژول‌های اختیاری و قالب.
- کنترلرها نازک باشند؛ منطق کسب‌وکار در Serviceها قرار گیرد.
- دسترسی مستقیم به دیتابیس فقط از Repositoryها و با Queryهای پارامتری.
- اعتبارسنجی ورودی در سمت سرور؛ اعتبارسنجی مرورگر صرفاً برای تجربه کاربری است.
- خروجی HTML به‌صورت پیش‌فرض escape شود؛ محتوای rich text با سیاست مجازسازی مشخص پاک‌سازی شود.
- همه عملیات تغییردهنده با احراز هویت، مجوز مناسب و CSRF محافظت شوند.
- قالب فقط از APIهای تعریف‌شده CMS به محتوا دسترسی داشته باشد.
- ساختار ذخیره‌سازی بلوک‌ها نسخه‌بندی شود تا مهاجرت قالب و محتوا ممکن باشد.
- قابلیت‌های جدید به‌صورت افزایشی توسعه یابند؛ بازنویسی کامل نسخه استاتیک در یک مرحله انجام نشود.

## 4. لایه‌های اصلی سیستم

### 4.1 Core

- Router و Middleware
- مدیریت درخواست و پاسخ HTTP
- مدیریت خطا و گزارش‌گیری
- اتصال PDO و مدیریت تراکنش
- سیستم Session و Authentication
- Role-Based Access Control
- اعتبارسنجی و پاک‌سازی ورودی
- Event/Hookهای داخلی محدود و مستند
- Registry و Lifecycle ماژول‌ها
- مدیریت Cache و تنظیمات محیط

### 4.2 Content Management

انواع محتوای اولیه:

- Page
- Article
- Project
- Skill
- Timeline Entry

فیلدهای مشترک محتوا: عنوان، slug یکتا، خلاصه، بدنه ساختاریافته، وضعیت، نویسنده، تصویر شاخص، تاریخ ایجاد/ویرایش/انتشار، SEO metadata و نسخه محتوا.

وضعیت‌ها: `draft`، `review`، `scheduled`، `published`، `archived`.

برای محتوای قابل انتشار، تاریخچه Revision مستقل نگهداری شود. ذخیره خودکار ویرایشگر باید به‌صورت draft/autosave انجام شود و هرگز بدون تأیید کاربر محتوای منتشرشده را بی‌صدا جایگزین نکند.

### 4.3 Block Editor

ویرایشگر محتوای غنی برای ساخت بدنه مقاله و صفحات:

- پاراگراف، عنوان، لیست و نقل‌قول
- تصویر، گالری، ویدئو و فایل
- کد با Syntax Highlighting
- جدول، لینک و جداکننده
- Embedهای مجاز و کنترل‌شده

محتوا با JSON ساختاریافته و دارای `schema_version` ذخیره شود. Tiptap گزینه پیشنهادی برای تجربه ویرایش است؛ بسته سمت مرورگر به‌صورت محلی و نسخه‌ثابت ارائه شود. HTML خام ورودی نباید مستقیماً اجرا شود.

### 4.4 Visual Page Builder

صفحه‌ساز از همان Block Registry استفاده کند تا بلوک‌ها بین ویرایشگر و صفحه‌ساز سازگار باشند.

قابلیت‌ها:

- افزودن، حذف، جابه‌جایی، تکرار و گروه‌بندی Sectionها با Drag & Drop
- پنل تنظیمات هر بلوک
- کنترل visibility و ترتیب در breakpointهای دسکتاپ، تبلت و موبایل
- کتابخانه Sectionهای ذخیره‌شده
- قالب‌های آماده برای صفحه اصلی، درباره، پروژه و تماس
- Preview زنده و حالت انتشار/پیش‌نویس
- Undo/Redo و ذخیره خودکار
- نمایش ساختار صفحه در Navigator

**محدودیت آگاهانه نسخه اول:** صفحه‌ساز یک سیستم بلوکی کنترل‌شده است، نه ویرایشگر آزاد HTML/CSS. کد سفارشی فقط در بخش جداگانه و با دسترسی مدیر و هشدار امنیتی قابل اضافه شدن است.

### 4.5 Theme Studio

- توکن‌های رنگ، تایپوگرافی، فاصله و radius
- فونت‌های محلی و fallback مناسب فارسی
- پوسته روشن، تاریک و پیروی از سیستم
- تنظیم هدر، فوتر، ناوبری و عرض محتوا
- تنظیمات breakpoint و حالت حرکت
- پیش‌نمایش تغییرات قبل از ذخیره/انتشار
- ذخیره تنظیمات قالب به‌شکل نسخه‌بندی‌شده

قالب `milad` نسخه فعلی طراحی مینیمال لوکس و آینده‌نگر را حفظ می‌کند. داده‌های محتوایی نباید در فایل‌های قالب hardcode شوند.

### 4.6 Media Manager

- آپلود چندفایلی و Drag & Drop
- پوشه، جست‌وجو، فیلتر و جزئیات فایل
- تولید thumbnail و نسخه‌های بهینه
- پشتیبانی از WebP و AVIF در صورت پشتیبانی محیط
- مدیریت alt text، عنوان و توضیحات
- تشخیص MIME از محتوای فایل، محدودیت حجم و نام‌گذاری امن
- جلوگیری از اجرای فایل آپلودشده
- نگهداری فایل‌های خصوصی خارج از DocumentRoot
- حذف امن با بررسی استفاده فایل در محتوا

### 4.7 Portfolio Module

- پروژه‌ها با وضعیت و دسته‌بندی
- لینک سایت، مخزن، مستندات و نسخه انتشار
- فناوری‌ها و برچسب‌ها
- پروژه‌های منتخب و ترتیب نمایش
- مهارت‌ها و سطح/دسته مرتبط
- Timeline و دستاوردها
- صفحه Now برای تمرکز فعلی
- اتصال اختیاری GitHub با توکن حداقل‌دسترسی، cache و به‌روزرسانی دستی/زمان‌بندی‌شده

دریافت داده از GitHub نباید به انتشار خودکار اطلاعات منجر شود؛ مدیر باید امکان بازبینی و تأیید داشته باشد.

## 6. امنیت و کنترل دسترسی

امنیت بخشی از طراحی اولیه است، نه مرحله پایانی.

- رمز عبور با `password_hash()` و الگوریتم امن پیش‌فرض PHP ذخیره شود.
- پس از ورود و تغییر سطح دسترسی، Session ID بازتولید شود.
- Cookie نشست با `HttpOnly`، `Secure` در HTTPS و `SameSite` مناسب تنظیم شود.
- CSRF token برای همه عملیات state-changing لازم باشد.
- Queryها با PDO prepared statements اجرا شوند.
- خروجی بر اساس context escape شود؛ HTML مجاز با allowlist پاک‌سازی شود.
- کنترل دسترسی در سمت سرور و برای هر عملیات/منبع اعمال شود.
- محدودیت نرخ ورود، تأخیر/قفل موقت و ثبت تلاش‌های ناموفق پیاده شود.
- اعتبارسنجی Origin/Host و جلوگیری از Host Header Injection در URLهای حساس انجام شود.
- فایل‌های آپلودی خارج از مسیر اجرایی، با نام تصادفی و MIME/extension کنترل‌شده ذخیره شوند.
- خطای داخلی و stack trace در production به کاربر نمایش داده نشود.
- کلیدها، رمزهای دیتابیس و secretها در فایل خارج از DocumentRoot یا متغیر محیطی باشند.
- عملیات حساس مانند ایجاد مدیر، تغییر نقش، حذف محتوا، بازیابی نسخه پشتیبان و تغییر تنظیمات امنیتی در Activity Log ثبت شوند.
- توکن GitHub و APIها با حداقل scope لازم ذخیره و هرگز در HTML یا log افشا نشوند.

نقش‌های پیش‌فرض: Owner، Administrator، Editor، Author و Viewer. مجوزها باید granular باشند؛ Viewer فقط خواندن داشته باشد و هر عملیات تغییردهنده در UI و مهم‌تر از آن در Backend مسدود شود.

## 7. Web Installer

مسیر نصب فقط در حالت نصب‌نشده فعال باشد.

### مراحل نصب

1. بررسی نسخه PHP، افزونه‌های موردنیاز، نوشتن فایل و قابلیت اتصال پایگاه داده.
2. دریافت اطلاعات اتصال MySQL/MariaDB و تست واقعی اتصال.
3. دریافت عنوان سایت، URL، زبان و منطقه زمانی.
4. ساخت حساب Owner و اعتبارسنجی رمز.
5. اجرای Migrationها در تراکنش‌های مناسب و Seed داده‌های پایه.
6. نوشتن تنظیمات محیطی خارج از DocumentRoot با permission محدود.
7. ساخت فایل/نشانگر قفل نصب و غیرفعال‌سازی دائمی مسیر نصب.
8. اجرای health check و هدایت به ورود پنل.

الزامات امنیتی:

- نصب مجدد از مسیر عمومی ممنوع باشد.
- وجود lock به‌تنهایی کافی نیست؛ وضعیت نصب از config و دیتابیس نیز اعتبارسنجی شود.
- عملیات نصب دارای CSRF و اعتبارسنجی ورودی باشد.
- خطاها بدون افشای credential یا SQL خام نمایش داده شوند.
- credentialها در log ثبت نشوند.
- installer در deployment نهایی در صورت نصب‌شدن غیرقابل اجرا باشد.
- نصب دمو اختیاری باشد و داده نمونه به‌صورت شفاف قابل انتخاب باشد.

## 8. مسیرها و API

مسیرهای عمومی:

- `/` صفحه اصلی
- `/projects/{slug}` صفحه پروژه
- `/articles/{slug}` مقاله
- `/about` درباره
- `/now` وضعیت فعلی
- `/contact` ارتباط

مدیریت:

- `/admin` داشبورد
- `/admin/content` مدیریت محتوا
- `/admin/editor/{id}` ویرایشگر
- `/admin/builder/{id}` صفحه‌ساز
- `/admin/media` رسانه
- `/admin/appearance` Theme Studio
- `/admin/users` کاربران و نقش‌ها
- `/admin/settings` تنظیمات
- `/install` فقط برای نصب اولیه

API:

- `/api/v1/pages`
- `/api/v1/projects`
- `/api/v1/articles`
- `/api/v1/media`
- `/api/v1/admin/...`

API عمومی فقط داده منتشرشده را برگرداند. API مدیریتی احراز هویت و مجوز مستقل داشته باشد. پاسخ‌ها، خطاها، pagination و نسخه‌بندی باید قرارداد یکنواخت داشته باشند.

## 9. برنامه اجرای مرحله‌ای

### فاز 0 — آماده‌سازی و قراردادهای پروژه

- ثبت معماری و ADRها
- تعریف قواعد کدنویسی، autoload و تنظیمات محیط
- ایجاد اسکلت پوشه‌ها و ورودی public
- تعریف روش migration، تست و deployment
- ثبت نسخه فعلی سایت برای حفظ امکان بازگشت

**معیار پذیرش:** برنامه روی محیط توسعه اجرا شود، health check قابل استفاده باشد و فایل‌های داخلی از وب قابل دسترسی نباشند.

### فاز 1 — هسته و زیرساخت

- Router، Request/Response و Middleware
- PDO، migration runner و repository پایه
- Config، logger، error handler و validation
- view renderer و layout پایه
- تست‌های واحد برای اجزای Core

**معیار پذیرش:** یک مسیر عمومی و یک مسیر مدیریتی آزمایشی با ساختار کنترلر/سرویس/Repository اجرا شوند و تست‌ها سبز باشند.

### فاز 2 — Installer، Authentication و RBAC

- نصب‌کننده مرحله‌ای
- ورود، خروج، تغییر رمز و مدیریت نشست
- نقش‌ها و مجوزهای granular
- CSRF، rate limit و Activity Log اولیه
- قفل نصب و تست نصب مجدد

**معیار پذیرش:** نصب تازه روی دیتابیس خالی موفق باشد؛ دسترسی غیرمجاز، CSRF و تلاش ورود پرتکرار مسدود شوند.

### فاز 3 — پنل مدیریت و هسته محتوا

- پوسته Admin با منو و داشبورد
- CRUD صفحات و نوشته‌ها
- slug، وضعیت انتشار، دسته و برچسب
- draft، preview و revision
- تنظیمات عمومی سایت

**معیار پذیرش:** مدیر بتواند بدون ویرایش فایل، صفحه و مقاله ایجاد، پیش‌نمایش، منتشر و نسخه قبلی را بازیابی کند.

### فاز 4 — Media Manager

- آپلود امن، کتابخانه رسانه و جست‌وجو
- thumbnail و metadata
- انتخاب رسانه از داخل ویرایشگر
- اعتبارسنجی MIME، حجم و مسیر ذخیره‌سازی

## 10. تست و کیفیت

حداقل سطوح تست:

- Unit: Router، validation، authorization، content services و block schema
- Integration: دیتابیس، migration، installer، login و media
- Feature: CRUD، preview، publish، revision و restore
- Security: CSRF، XSS، SQL injection، IDOR، session fixation، upload bypass و privilege escalation
- UI: موبایل، دسکتاپ، RTL، کیبورد و reduced motion
- Deployment: نصب روی هاست خالی و اجرای سایت بدون Node.js

هیچ فاز نباید صرفاً با «ظاهر شدن صفحه» پذیرفته شود؛ معیارهای کارکردی و امنیتی همان فاز باید پاس شوند.

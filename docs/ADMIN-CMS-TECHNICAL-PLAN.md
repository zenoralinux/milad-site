# سند فنی تبدیل Milad Site به وب‌سایت پویا و CMS اختصاصی

- وضعیت سند: طرح اجرایی پیشنهادی
- نسخه: 1.0
- تاریخ: 2026-11-14
- شاخه مبنا: `redesign/minimal-luxury-futuristic-20261113`
- هدف: تبدیل پرتفولیوی استاتیک فعلی به یک وب‌سایت پویا با پنل مدیریت اختصاصی، بدون بازطراحی ناخواسته رابط عمومی.

---

## 1. خلاصه تصمیم‌های فنی

### وضعیت فعلی مخزن

بررسی شاخه مبنا نشان می‌دهد:

- صفحه اصلی در `index.html` پیاده‌سازی شده است.
- ساختار فعلی شامل Hero، پروژه‌ها، درباره من، اصول کاری، بخش «اکنون»، ارتباط و Footer است.
- پنج پروژه مستقیماً در HTML نوشته شده‌اند: Zenora Linux، ZenoraChat Web، ZenoraChat Android، Zenora Android و Zenora WSL.
- دسته‌بندی فعلی پروژه‌ها از مقادیر `os`، `apps` و `tools` استفاده می‌کند.
- فایل `assets/js/site.js` مسئول رفتارهای سمت کاربر مانند پوسته روشن/تیره، منوی موبایل، Command Palette، فیلتر پروژه‌ها، نوار پیشرفت و انیمیشن ورود بخش‌هاست.
- CSS و تعاملات فعلی فرانت‌اند به فریم‌ورک خاصی وابسته نیستند.
- در مخزن فعلی بک‌اند، دیتابیس، احراز هویت یا پنل مدیریت وجود ندارد.

### انتخاب معماری

| لایه | انتخاب |
|---|---|
| رابط عمومی | HTML معنایی، CSS و JavaScript فعلی |
| رندر صفحات عمومی | PHP Server-Side Rendering |
| بک‌اند | PHP 8.2 یا جدیدتر |
| اتصال دیتابیس | PDO با Prepared Statements |
| دیتابیس | MySQL 8 یا MariaDB 10.6+ |
| قرارداد API | REST-style JSON برای عملیات پنل |
| احراز هویت | PHP Session امن |
| ویرایش محتوا | فرم‌های ساختاریافته؛ Markdown برای متن‌های بلند در مراحل بعد |
| وابستگی‌ها | حداقل وابستگی؛ بدون اجبار به Node.js یا Build Step |

**تصمیم مهم:** در فاز اول ظاهر سایت از نو نوشته نمی‌شود. کلاس‌های CSS، ساختار بصری کارت پروژه‌ها، شناسه بخش‌ها، رفتار واکنش‌گرا و تعاملات فعلی تا حد ممکن حفظ می‌شوند. تغییر اصلی، جایگزینی داده‌های Hard-coded با داده‌های خوانده‌شده از دیتابیس است.

### پیش‌شرط انتشار

سایت فعلی استاتیک است. اجرای PHP و اتصال MySQL روی GitHub Pages یا هاست استاتیک ممکن نیست. برای نسخه پویا باید محیط انتشار دارای PHP، MySQL/MariaDB و HTTPS باشد. وضعیت هاست فعلی و امکان اجرای PHP هنوز از مخزن قابل تشخیص نیست؛ پیش از انتشار عملیاتی باید این مورد بررسی شود.

7. ثبت رویدادهای مهم مدیریتی.
8. آماده بودن ساختار برای افزودن وبلاگ، رسانه، پیام‌ها و آمار در مراحل بعد.

- Page Builder آزاد با Drag & Drop

این موارد در طراحی کلی دیده شده‌اند، اما نباید تحویل فاز اول را پیچیده یا به تأخیر بیندازند.

## 3. ساختار پیشنهادی مخزن

ساختار زیر هدف معماری است؛ در پیاده‌سازی باید تغییرات به‌صورت تدریجی انجام شود و فایل‌های فعلی بی‌دلیل جابه‌جا یا بازنویسی نشوند.

```text
/
├── app/
│   ├── Controllers/
│   │   ├── Admin/
│   │   └── Public/
│   ├── Core/
│   │   ├── Auth.php
│   │   ├── Csrf.php
│   │   ├── Database.php
│   │   ├── Router.php
│   │   ├── Validator.php
│   │   └── View.php
│   ├── Repositories/
│   ├── Services/
│   └── Views/
│       ├── admin/
│       └── public/
├── bin/
│   └── create-admin.php
├── config/
│   └── app.example.php
├── database/
│   └── migrations/
├── docs/
├── public/
│   ├── admin/
│   ├── api/
│   ├── assets/
│   ├── favicon.svg
│   ├── index.php
│   ├── milad_avatar.jpg
│   ├── og-image.svg
│   ├── robots.txt
│   └── sitemap.xml
└── storage/
    ├── logs/
    ├── cache/
    └── uploads/
```

نکات اجرایی:

- `public/` باید Document Root وب‌سرور باشد تا فایل‌های `app/`، `config/` و `storage/` مستقیماً از وب قابل دسترسی نباشند.
- فایل‌های حساس مانند رمز دیتابیس و کلیدهای محیطی نباید در Git ثبت شوند.
- فایل `config/app.example.php` فقط نمونه نام و شکل تنظیمات را نگه می‌دارد؛ تنظیمات واقعی خارج از Document Root قرار می‌گیرند.
- اگر هاست فعلی امکان تعیین Document Root ندارد، باید با تنظیمات وب‌سرور دسترسی مستقیم به مسیرهای حساس کاملاً مسدود شود.
- فایل‌های فعلی CSS، JavaScript، تصویر پروفایل، favicon و OG image در انتقال حفظ می‌شوند.
- مسیرهای فعلی مثل `/assets/css/site.css` باید با تنظیم Document Root یا Rewrite حفظ شوند.

## 4. مدل داده و دیتابیس

دیتابیس با `utf8mb4` و موتور InnoDB ساخته شود. زمان‌ها در دیتابیس UTC ذخیره و هنگام نمایش با منطقه زمانی سایت قالب‌بندی شوند. تمام ارتباط‌ها با کلید خارجی و ایندکس مناسب تعریف شوند.

### 4.1 جدول `admin_users`

| ستون | نوع پیشنهادی | توضیح |
|---|---|---|
| id | BIGINT UNSIGNED | کلید اصلی |
| username | VARCHAR(80) | نام کاربری یکتا |
| password_hash | VARCHAR(255) | خروجی password_hash |
| display_name | VARCHAR(120) | نام نمایشی |
| role | VARCHAR(30) | در نسخه اول فقط owner |
| is_active | BOOLEAN | امکان غیرفعال کردن حساب |
| last_login_at | DATETIME NULL | آخرین ورود موفق |
| created_at / updated_at | DATETIME | تاریخ ایجاد و ویرایش |

ثبت‌نام عمومی مدیر وجود ندارد. اولین حساب با اسکریپت CLI یا فرمان راه‌اندازی امن ساخته می‌شود. رمز اولیه نباید در کد یا Seed عمومی قرار گیرد.

### 4.2 جدول `admin_login_attempts`

برای محدودیت تلاش ورود:

- `id`
- `identity_hash` برای شناسه ورود Hash‌شده
- `ip_hash` برای IP Hash‌شده
- `attempted_at`
- `was_successful`

سیاست اولیه پیشنهادی: بعد از 5 تلاش ناموفق در بازه 15 دقیقه، ورود برای همان ترکیب شناسه/IP به‌صورت موقت محدود شود. مقدارها باید قابل تنظیم باشند و پاسخ خطا وجود یا عدم وجود نام کاربری را افشا نکند.

### 4.3 جدول `site_settings`

| ستون | نوع | توضیح |
|---|---|---|
| setting_key | VARCHAR(120) PK | کلید یکتا |
| setting_value | LONGTEXT | مقدار ساده یا JSON معتبر |
| value_type | VARCHAR(20) | string، boolean، json |
| updated_at | DATETIME | آخرین تغییر |
| updated_by | BIGINT NULL | مدیر تغییر‌دهنده |

کلیدهای اولیه پیشنهادی:

- `site.name`
- `site.description`
- `site.canonical_url`
- `site.default_theme`
- `site.maintenance_mode`
- `contact.github_url`
- `contact.telegram_url`
- `profile.avatar_path`

اطلاعات حساس یا رمزها نباید در این جدول نگه‌داری شوند.

### 4.4 جدول `site_sections`

برای بخش‌های ساختاری صفحه اصلی:

| ستون | نوع | توضیح |
|---|---|---|
| id | BIGINT UNSIGNED PK | شناسه |
| section_key | VARCHAR(60) UNIQUE | کلید ثابت مثل hero یا about |
| content_json | JSON یا LONGTEXT | داده‌های همان بخش |
| is_visible | BOOLEAN | نمایش یا عدم نمایش |
| sort_order | INT | ترتیب نمایش |
| updated_at | DATETIME | آخرین تغییر |
| updated_by | BIGINT NULL | مدیر ویرایش‌کننده |

کلیدهای اولیه:

- `hero`: عنوان، متن معرفی، متن و لینک دکمه‌ها، برچسب وضعیت
- `intro`: متن نوار معرفی
- `about`: عنوان، توضیحات و لینک
- `principles`: آرایه اصول و توضیحات آن‌ها
- `now`: عنوان، متن و وضعیت فعلی
- `contact`: عنوان و متن راه‌های ارتباطی
- `footer`: متن پایانی و اطلاعات کپی‌رایت

ساختار JSON هر بخش باید در بک‌اند Schema و Validation مشخص داشته باشد. HTML خام دریافتی از مدیر مستقیماً رندر نشود؛ داده‌ها Escape شوند و قالب HTML در View باقی بماند.

### 4.5 جدول `projects`

| ستون | نوع | توضیح |
|---|---|---|
| id | BIGINT UNSIGNED PK | شناسه |
| slug | VARCHAR(160) UNIQUE | شناسه URL |
| title | VARCHAR(180) | عنوان |
| category | VARCHAR(40) | os، apps، tools یا دسته جدید |
| kind_label | VARCHAR(100) | برچسب نوع پروژه |
| excerpt | VARCHAR(500) | توضیح کارت |
| description | LONGTEXT NULL | توضیحات کامل |
| status | VARCHAR(30) | active، in_progress، paused، archived |
| visual_variant | VARCHAR(60) | کلید کلاس بصری مجاز |
| is_featured | BOOLEAN | پروژه ویژه |
| is_published | BOOLEAN | وضعیت انتشار |
| sort_order | INT | ترتیب |
| published_at | DATETIME NULL | تاریخ انتشار |
| created_at / updated_at | DATETIME | زمان ایجاد و ویرایش |

داده اولیه باید از همان پنج پروژه فعلی مهاجرت کند. وضعیت و لینک هر پروژه در زمان مهاجرت دقیقاً از محتوای فعلی حفظ شود.

### 4.6 جدول‌های وابسته پروژه

`project_links`:

- id، project_id، label، url، link_type، sort_order
- حذف پروژه، لینک‌های وابسته را با Foreign Key مناسب حذف کند.
- فقط URLهای مجاز مانند HTTPS و مسیرهای داخلی معتبر پذیرفته شوند.

`project_technologies`:

- id، project_id، name، sort_order
- برای تگ‌های Technology هر پروژه استفاده شود.

### 4.7 جدول `admin_activity_logs`

برای ثبت رویدادهای مدیریتی:

- id
- admin_user_id
- action
- entity_type
- entity_id
- summary
- ip_hash
- created_at

رمز عبور، توکن نشست، محتوای محرمانه یا داده حساس نباید در Log ذخیره شود.

### 4.8 جداول مراحل بعد

این موارد در مرحله مربوط ساخته می‌شوند، نه به‌صورت شتاب‌زده در فاز اول:

- `media_assets`: مسیر فایل، MIME واقعی، اندازه، ابعاد، متن جایگزین، زمان آپلود
- `contact_messages`: نام، ایمیل، موضوع، متن، وضعیت، زمان دریافت
- `posts`: slug، عنوان، خلاصه، بدنه Markdown، تصویر شاخص، وضعیت انتشار، تاریخ انتشار
- `post_categories` و `post_tags`
- `content_revisions`: نسخه‌های قبلی بخش‌ها و پروژه‌ها
- `analytics_daily`: آمار تجمیعی روزانه و بدون ذخیره غیرضروری اطلاعات شخصی

## 5. صفحات پنل مدیریت

مسیر پایه پنل: `/admin`

| مسیر | صفحه | دسترسی |
|---|---|---|
| /admin/login | ورود مدیر | عمومی |
| /admin | داشبورد | مدیر واردشده |
| /admin/content | مدیریت بخش‌های صفحه اصلی | مدیر واردشده |
| /admin/projects | فهرست پروژه‌ها | مدیر واردشده |
| /admin/projects/new | پروژه جدید | مدیر واردشده |
| /admin/projects/{id}/edit | ویرایش پروژه | مدیر واردشده |
| /admin/settings | تنظیمات عمومی سایت | مدیر واردشده |
| /admin/activity | تاریخچه فعالیت‌ها | مدیر واردشده |

### داشبورد

نسخه اول فقط شاخص‌های واقعی و قابل محاسبه را نشان دهد:

- تعداد کل پروژه‌ها
- تعداد پروژه‌های منتشرشده
- تعداد پروژه‌های پیش‌نویس
- آخرین تغییرات مدیریتی
- میان‌بر ایجاد پروژه و ویرایش محتوای صفحه

تا زمان پیاده‌سازی Analytics، نمودار بازدید یا اعداد ساختگی نمایش داده نشود.

### مدیریت محتوای صفحه

- تب یا فهرست بخش‌ها با نام قابل فهم فارسی
- ویرایش هر بخش در فرم اختصاصی
- فعال/غیرفعال کردن بخش
- اعتبارسنجی طول متن و URL
- ذخیره و نمایش پیام موفقیت/خطا
- امکان بازگشت به مقدار ذخیره‌شده هنگام لغو ویرایش
- پیش‌نمایش در مرحله بعدی؛ در نسخه اول حداقل Preview امن یا لینک مشاهده صفحه کافی است.

### مدیریت پروژه

- فهرست با جست‌وجو و فیلتر دسته و وضعیت
- ایجاد، ویرایش، انتشار، لغو انتشار و حذف با تأیید
- مدیریت لینک‌ها و Technology Tags
- انتخاب پروژه ویژه
- مرتب‌سازی با کنترل بالا/پایین در نسخه اول؛ Drag & Drop می‌تواند بعداً اضافه شود
- تولید خودکار slug با امکان اصلاح دستی
- جلوگیری از تکرار slug

## 6. قرارداد API

API پنل در مسیر `/api/admin/v1` و با پاسخ JSON استاندارد ساخته شود.

### قالب پاسخ موفق

```json
{
  "ok": true,
  "data": {},
  "message": "تغییرات ذخیره شد."
}
```

### قالب پاسخ خطا

```json
{
  "ok": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "اطلاعات ارسالی معتبر نیست.",
    "fields": {}
  }
}
```

### Endpointهای فاز اول

| Method | مسیر | عملکرد |
|---|---|---|
| POST | /api/admin/v1/auth/login | ورود |
| POST | /api/admin/v1/auth/logout | خروج |
| GET | /api/admin/v1/auth/session | وضعیت نشست |
| GET | /api/admin/v1/dashboard | خلاصه داشبورد |
| GET | /api/admin/v1/sections | دریافت بخش‌ها |
| PUT | /api/admin/v1/sections/{key} | ویرایش بخش |
| GET | /api/admin/v1/projects | فهرست و فیلتر پروژه‌ها |
| POST | /api/admin/v1/projects | ایجاد پروژه |
| GET | /api/admin/v1/projects/{id} | دریافت جزئیات |
| PUT | /api/admin/v1/projects/{id} | ویرایش پروژه |
| DELETE | /api/admin/v1/projects/{id} | حذف پروژه |
| POST | /api/admin/v1/projects/reorder | ذخیره ترتیب |
| GET | /api/admin/v1/settings | دریافت تنظیمات |
| PUT | /api/admin/v1/settings | ذخیره تنظیمات |

تمام Endpointهای غیر از Login باید احراز هویت و مجوز لازم را بررسی کنند. تمام درخواست‌های تغییردهنده داده باید CSRF Token معتبر داشته باشند.

صفحه عمومی بهتر است در سمت سرور از Repositoryها داده دریافت کند و HTML نهایی را تولید کند. این تصمیم از خالی ماندن صفحه در صورت شکست JavaScript جلوگیری می‌کند و SEO فعلی را حفظ می‌کند. API عمومی در صورت نیاز برای مصرف‌های بعدی اضافه می‌شود.

## 7. امنیت و کنترل دسترسی

موارد زیر شرط تحویل هستند:

1. Hash رمز با `password_hash(PASSWORD_DEFAULT)` و بررسی با `password_verify`.
2. اجرای `session_regenerate_id(true)` بعد از ورود موفق.
3. کوکی Session با `HttpOnly`، `SameSite=Lax` و در محیط HTTPS با `Secure`.
4. CSRF Token برای تمام عملیات تغییردهنده.
5. محدودیت نرخ ورود و پاسخ یکسان برای نام کاربری نامعتبر و رمز اشتباه.
6. کوئری‌های دیتابیس فقط با PDO Prepared Statements.
7. Escape خروجی HTML با `htmlspecialchars` و UTF-8.
8. اعتبارسنجی سمت سرور برای همه فیلدها، حتی اگر رابط کاربری Validation داشته باشد.
9. کنترل مجوز در هر درخواست؛ مخفی کردن دکمه در UI کافی نیست.
10. محدودسازی CORS؛ API مدیریتی برای Originهای نامعلوم باز نباشد.
11. عدم ذخیره Secret در مخزن و جلوگیری از دسترسی HTTP به `config/` و `storage/`.
12. اجبار HTTPS در محیط Production.
13. ثبت رویداد ورود و تغییرات مهم بدون ثبت داده حساس.
14. Backup دیتابیس و آزمایش واقعی Restore پیش از انتشار عمومی.

در فاز اول فقط نقش `owner` فعال است، اما ستون نقش از ابتدا وجود دارد تا بعداً نقش‌های `editor` و `viewer` بدون بازطراحی اساسی اضافه شوند.

## 8. حفظ ظاهر و مهاجرت فرانت‌اند

این قسمت برای جلوگیری از خراب شدن طراحی فعلی حیاتی است:

- فایل CSS فعلی به‌عنوان منبع طراحی حفظ شود.
- JavaScript فعلی برای Theme، منو، فیلترها، Command Palette و Reveal حفظ و فقط در نقاط نیازمند داده پویا تطبیق داده شود.
- فیلتر پروژه‌ها باید از `data-category` موجود استفاده کند.
- کلاس‌های بصری کارت‌ها با `visual_variant` مجاز تولید شوند؛ مدیر نباید بتواند کلاس دلخواه یا HTML اجرایی وارد کند.
- ترتیب پروژه‌ها از `sort_order` خوانده شود.
- پروژه‌های منتشرنشده در صفحه عمومی نمایش داده نشوند.
- بخش‌های غیرفعال در HTML عمومی خروجی داده نشوند.
- عنوان، توضیحات، Canonical، Open Graph و JSON-LD از داده معتبر سایت تولید شوند.
- آدرس‌های فعلی و Anchor IDهای `#home`، `#work`، `#about`، `#now` و `#contact` حفظ شوند.
- حالت تاریک/روشن و ترجیح ذخیره‌شده کاربر همچنان در مرورگر کار کند.
